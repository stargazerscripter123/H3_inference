Q:

对于双5090 来说，现在 TE 的quantization是个问题（bf16 占太多 5090 VRAM），我应该怎么在双5090 上跑 tensor parallel 的 H3

A:

# 结论

按你的机器：

```text
2 × RTX 5090 32GB
128GB system RAM
MiniMax H3 FL2VA
目标：TP2 + Turbo LoRA + 864×480 接近 30 秒
```

正确架构不是让 **BF16 TE 和 DiT 同时常驻两张卡**，而是：

> **FP8 DiT 做 TP2，并尽量常驻；FP8 TE 也做 TP2，但只在 encoding 阶段按层载入，encode 完立即卸载；VAE 同样按阶段载入。**

即：

```text
                GPU 0                         GPU 1
        ┌──────────────────┐          ┌──────────────────┐
Encode  │ FP8 TE shard 0   │  TP2     │ FP8 TE shard 1   │
        │ layer-by-layer   │◀────────▶│ layer-by-layer   │
        └────────┬─────────┘          └────────┬─────────┘
                 └──── BF16 [S,5120] embeddings ────┘
                              │
                    TE weights 返回 CPU
                              │
        ┌──────────────────┐          ┌──────────────────┐
Denoise │ FP8 DiT shard 0  │  TP2     │ FP8 DiT shard 1  │
        │ 尽可能全常驻       │◀────────▶│ 尽可能全常驻       │
        └────────┬─────────┘          └────────┬─────────┘
                 └──────── AV latents ─────────┘
                              │
                  tiled / staged VAE decode
```

**TE quantization 的主要意义是解决容量和 PCIe 传输，不是直接降低大量延迟。**vLLM-Omni 的实测中，TP2 TE 的 Linear 权重从每个 rank 的 22.705GiB BF16 降到 11.353GiB FP8，但短请求反而慢了约 3.3%；它本质上是内存优化。

真正决定你能否进入 30 秒的是：

1. Turbo 把 DiT forward 降到 4–6 NFE；
2. DiT 在 denoise 期间不能每个 block 都从 CPU 搬进来；
3. TE 不能在 denoise 阶段占着十几 GB 显存；
4. VAE 不能和 TE、DiT 同时常驻。

# 一、为什么单纯 `text_encoder_tp_size=2` 仍然不够

H3 保留的 Qwen3-VL TE 约 51.5GB BF16。它虽然能 TP2，但每张卡仍要承担约一半权重，而且最终 `[seq, 5120]` hidden state 会在两个 encoder rank 上保持完整副本。

粗略内存账如下：

| 组件                               |       TP2 每卡内存 |
| -------------------------------- | -------------: |
| BF16 TE Linear 权重                |      22.705GiB |
| FP8 TE Linear 权重                 |      11.353GiB |
| TE vision tower、embedding、norm 等 |       约 2–4GiB |
| FP8 DiT TP2 权重及非量化模块             | 约 18–22GiB，需实测 |
| 864×480×124 activation/workspace |          数 GiB |
| VAE                              |         需要额外空间 |

因此即使 TE 变成 FP8：

```text
FP8 TE 约 13–15GB/GPU
+
FP8 DiT 约 18–22GB/GPU
+
activations / VAE
```

仍然无法舒服地同时放进 32GB。

所以一定要做：

```text
TE quantization
+
TE stage offload
+
DiT TP2
```

而不是：

```text
TE quantization
+
TE 与 DiT 永久同时 resident
```

# 二、我建议的主生产路线：SGLang staged TP2

## 为什么主推 SGLang

SGLang 的 Qwen3-VL 实现已经具备：

* quantized Linear；
* column/row tensor parallel；
* FP8 weight path；
* encoder folding；
* component-level layerwise offload。

其 `Qwen3VLTextModel` 已能把 `quant_config` 传给 attention 和 MLP 的 q/k/v/o、gate/up/down projections，并支持 TP Linear。H3 原先缺失的只是把 quantization config 接入 H3 wrapper。

当前开放的 SGLang PR #33681 正在补这个连接。它支持用：

```bash
--text-encoder-path /path/to/Qwen3-VL-32B-Instruct-FP8
```

替换 H3 TE，并已在 **2×RTX 5090、TP2** 上完成 Ref2VA 质量测试；它保留 vision tower、embedding、norm 和 RoPE 为原精度，只量化语言模型 Linear。

SGLang 的 `encoder-parallel=fold` 会在 encoding 阶段把宽 TE TP-shard 到空闲的 DiT replica 上，非常适合当前单请求延迟场景。

---

## 推荐 SGLang topology

```text
DiT:
  TP = 2
  Ulysses = 1
  FP8
  resident

TE:
  FP8
  encoder_parallel = fold
  layerwise offload
  encode 阶段逐层预取
  encode 后完全离开 GPU

VAE:
  layerwise/stage offload
  decode 阶段才载入

Turbo:
  离线 merge 到 BF16 DiT
  再由 engine 做 FP8
```

不要用：

```text
TP1 + Ulysses2
```

因为它只切 sequence，不切 66GB DiT 权重。双 32GB 卡必须先通过 TP2 切权重。

也不要用：

```text
TP2 + Ulysses2
```

因为这需要四个并行 rank。双卡时保持：

```text
TP2 × Ulysses1
```

这里最关键的是：


```text
text_encoder,vae
```


PR #33681 自己在全 memory profile 下，即使 TE 使用 FP8，host steady RSS 仍约 172GiB，所以你不能直接照搬它的：

```bash
--performance-mode memory
--layerwise-offload-components dit,text_encoder,vae
```

你需要的是：

```text
DiT resident
TE/VAE offload
```

而不是所有组件都 offload。

# 三、最容易先跑通的路线：vLLM-Omni global FP8 + DLO

如果 SGLang 的 resident FP8 DiT 在 5090 上暂时 OOM，先用 vLLM-Omni 的 global FP8 DLO 路线建立可运行基线。

## 不要只使用 TE FP8 PR

vLLM-Omni PR #5873 只解决 TE online FP8。它能把每 rank 的 TE Linear state 从 22.705GiB 降到 11.353GiB，但没有解决：

* DiT FP8 与 DLO 的完整结合；
* 冷启动量化峰值；
* quantized layer 返回 CPU；
* DLO quantized stride。

更合适的是较新的 PR #5910。它把全局：

```bash
--quantization fp8
```

扩展到：

```text
DiT eligible linears
+
TE eligible linears
```

并允许和 rank-local DLO 一起使用：

```bash
--enable-distributed-layerwise-offload
--dlo-no-use-allgather
```

该分支还会在 TE 一次性 encode 完成后把已经量化的 TE 返回 CPU，不会让它继续占用 denoise 阶段的 VRAM。

## 不要把 `resident-layers=20` 当成最终值

20 是 BF16 2×5090 capacity baseline。加上全局 FP8 后，你应该逐步提高：

```text
20
24
28
32
36
40
44
48
50
```

每次都用相同：

```text
864×480
124 frames
Turbo 6 NFE
同一 prompt
同一 seed
```

做 exact-shape warmup。

停止条件：

```text
peak VRAM >= 30.5–31GB
或
CUDA OOM
或
出现 allocator fragmentation
```

目标不是一定达到 50 层 resident，而是让每次 forward 需要从 CPU stream 的 block 数尽可能少。

例如：

```text
resident 20:
每次 forward stream 30 blocks

resident 40:
每次 forward stream 10 blocks

resident 50:
DiT block streaming 基本消失
```

Turbo 只有 4–6 NFE，所以即使仍有 5–10 个 nonresident block，也可能达到可接受延迟。

# 四、128GB RAM 的现实边界

官方 BF16 vLLM-Omni 5090 recipe 要求：

```text
最低可用 RAM：200GiB
推荐：384GiB
```

因为 DLO 会在 host 保留 rank-local pinned master weights；增加 resident layers 也不会自动删除 CPU master。

Global FP8 会显著缩小这些权重，但 PR #5910 目前没有公开：

```text
2×5090 + 128GB RAM
```

的完整 host RSS 数据。

所以 128GB 上必须设硬门槛。

启动前：

```bash
free -h
grep -E 'MemAvailable|SwapTotal|SwapFree' /proc/meminfo
```

运行期间：

```bash
watch -n 1 '
ps -C python -o pid,rss,vsz,cmd --sort=-rss | head
free -h
'
```

另一个终端：

```bash
vmstat 1
```

必须保持：

```text
si = 0
so = 0
```

我建议：

```text
启动前 MemAvailable >= 110GiB
总 RSS >= 115GiB 时主动停止
不得依赖 NVMe swap
只加载 FL2VA
不得同时开 Comfy/SGLang/其他大模型
```

如果 global FP8 DLO 仍超过 128GB，正确处理不是加 swap，而是：

```text
使用 pre-quantized checkpoint
或
升级到 192/256GB RAM
或
转向 SGLang 的 resident-DiT / TE-only-offload 架构
```

# 五、为什么 FP8 TE 是第一选择，而不是立即做 NVFP4

当前两条已经有验证的路线都是 FP8：

* vLLM-Omni online FP8 TE；
* SGLang pre-quantized FP8 Qwen3-VL TE。

vLLM-Omni 的测试中，FP8 TE 对最终视频的 PSNR 为 53.97dB，MAE 为 0.001024；说明 conditioning 差异相对较小。

SGLang 的 2×5090测试也没有观察到明显的 identity、服装、动作、光照和相机运动回退。

NVFP4 的确更省：

```text
FP8 TE：
约 11.35GiB Linear / rank

NVFP4/AWQ TE：
理论上可进一步降到约 6–8GiB / rank
```

但目前：

```text
Comfy NVFP4/AWQ TE
≠
vLLM-Omni/SGLang H3 可直接加载的 TP checkpoint
```

两边都没有已合并的 H3 NVFP4 TE TP2 loader。

所以执行顺序应该是：

```text
1. FP8 TE + TE-only offload
2. 证明 DiT 可以 resident
3. 证明总体低于或接近目标
4. 只有还差显存/传输时间时，再做 NVFP4
```

而不是先投入一轮新的 NVFP4 loader 工程。

如果最终确实需要 NVFP4，我会基于 **SGLang** 做，而不是 vLLM-Omni。原因是 SGLang 的 Qwen3-VL runtime 已经把 quantization abstraction 接到了 q/k/v/o 和 MLP Linear 上；H3 wrapper 只需要扩展 quantization-config 解析和 checkpoint loader。

# 六、如果 FP8 DiT 仍无法全 resident

按这个顺序处理。

## 1. 确认 VAE 没有占着 denoise 显存

Denoise 阶段只应该有：

```text
DiT TP shard
packed AV activations
scheduler buffers
NCCL workspace
```

不应同时有：

```text
完整 TE
完整 video VAE decoder
完整 audio VAE decoder
```

## 2. TE 必须只按层载入

不要把整个 FP8 TE 放进 GPU 后再 encode。使用：

```text
one-layer prefetch
encode
release
```

因为 TE 只执行一次，即使 PCIe 搬 50 层，也远好于每个 DiT NFE 搬 50 层。

## 3. 提高 DiT resident layers

这是 DLO 路线最直接的速度杠杆。

## 4. 引入 AdaLN schedule pruning/cache

H3 的 50 个 block AdaLN projections 加起来约 13B 参数，而且它们的输出只依赖有限的 timestep schedule，不依赖 prompt 或 latent。

vLLM-Omni 的 exact-schedule cache 实验在 TP2 BF16 下，每张 GPU：

```text
释放 AdaLN projection weights：12.144GiB
安装 schedule tables：0.885GiB
净释放：11.259GiB/GPU
```

并保持输出 byte-identical。

对于 Turbo production，你只有几个固定 schedule：

```text
4 NFE
6 NFE
8 NFE
video shift 12
audio shift 3
```

所以更适合：

```text
Turbo LoRA merge
→ 为 4/6/8 NFE 离线计算 AdaLN tables
→ 删除或不加载 AdaLN projection weights
→ 再 FP8 quantize 其余 DiT
```

注意：Turbo LoRA 本身包含 AdaLN delta，因此 schedule table 必须由 **Turbo merged model** 生成，不能复用 base H3 的表。

这一步很可能是把：

```text
40 resident blocks
```

推进到：

```text
50 resident blocks
```

的关键。

不过当前 PR 的首次 table build 会同时存在 projection weights 和 tables，cold peak 很高。双 5090 上应：

```text
使用 DLO 分层生成
或
离线生成表
```

不要直接在 resident 32GB 环境里冷构建整套表。

# 八、最终建议的 production profile

我建议最终目标配置是：

```yaml
engine: SGLang
topology:
  gpus: 2
  dit_tp: 2
  ulysses: 1
  encoder_parallel: fold

dit:
  checkpoint: Turbo-LoRA merged BF16
  runtime_precision: FP8
  placement: resident
  nfe: 6

text_encoder:
  checkpoint: Qwen3-VL-32B FP8
  tp: 2
  placement: layerwise stage offload
  output_dtype: BF16
  vision_tower: BF16

vae:
  placement: stage offload
  decode: tiled

video:
  resolution: 864x480
  frames: 124
  fps: 24

sampling:
  video_shift: 12
  audio_shift: 3
```

如果 SGLang 的 resident FP8 DiT 在双 5090 上暂时跑不通，则使用：

```yaml
engine: vLLM-Omni PR5910
global_fp8: true
tp: 2
text_encoder_tp: 2
dlo_no_allgather: true
resident_layers: 尽可能高
nfe: 6
```

作为过渡。

**最终优先级是：**

```text
DiT 不做 per-step offload
>
Turbo 少 NFE
>
TE FP8 stage offload
>
VAE stage offload
>
TE NVFP4
```

不要把大量工程时间先花在 NVFP4 TE 上。对 30 秒目标而言，TE 只运行一次；DiT 是否在每个 forward 传输权重，影响远大于 TE 从 FP8 再降到 4-bit。
