Q：

okay，我现在升级了机器：有4张5090， 574G RAM 和 1TB ssd

A：

太好了。现在这台机器是：

```text
4 × RTX 5090 32GB = 128GB 总显存
约 574GB 系统内存
1TB 本地 SSD
```

这次升级会让 H3 的最优路线发生根本变化：

> **不再把 global FP8＋每步 DLO 当作生产必需条件。先用 4 卡 TP 把 BF16 Turbo H3 跑到目标速度；FP8 降级为后续锦上添花的优化。**

你之前双 5090 上最大的矛盾是：

```text
不用 FP8 → 模型放不下
使用 FP8 → SM120 数值路径输出噪声
```

现在可以绕开这个死结：

```text
BF16 DiT TP4
+ TE/VAE 分阶段放置
+ Turbo 4–6 NFE
+ 不在 denoise 期间搬 DiT block
```

这条路线很可能已经足以让 864×480 的 5 秒视频进入 30 秒以内。

# 一、现在的生产主线应该改成什么

## 推荐主架构

```text
                   4 × RTX 5090
                         │
          ┌──────────────┴──────────────┐
          │                             │
     Encoding stage                Denoise stage
          │                             │
   Qwen3-VL BF16 TP4              H3 DiT BF16 TP4
   endpoint VAE encode            Turbo 4–6 NFE
   TE 按阶段加载                   DiT 全程 GPU resident
          │                             │
          └────────── embeddings ───────┘
                         │
                    Decode stage
                         │
                 Video VAE tile4
                 Audio VAE decode
                 NVENC / MP4 mux
```

核心原则是：

```text
TE、DiT、VAE 不需要同时常驻
DiT 在所有 denoise forward 之间必须常驻
```

H3 的 TE 只执行一次，VAE 只在首尾阶段执行；只有 DiT 会执行 4、6 或 8 次。因此资源优先级应是：

```text
DiT resident
>
减少 NFE
>
四卡并行
>
TE/VAE stage offload
>
FP8
```

# 二、为什么 BF16 TP4 现在可能是最优路线

H3 DiT BF16 约 66GB，TP4 后粗略为：

```text
66GB / 4 ≈ 16.5GB/GPU
```

Qwen3-VL TE BF16 约 51.5GB，TP4 后粗略为：

```text
51.5GB / 4 ≈ 12.9GB/GPU
```

两者同时常驻，再加 activation、VAE 和 NCCL workspace，仍然会超过单卡 32GB。但你现在有足够的系统内存，可以执行**组件级阶段切换**：

### Encoding 阶段

```text
TE TP4 在 GPU
DiT 部分或全部留在 CPU
VAE encoder 按需加载
```

### Denoise 阶段

```text
TE 完全返回 CPU
VAE 返回 CPU
DiT TP4 全部进入 GPU
```

### Decode 阶段

```text
DiT 释放部分显存
Video VAE tile4 解码
Audio VAE 解码
```

这与之前的 DLO 不同。之前是：

```text
每个 denoise step
  × 每个 nonresident block
  × CPU → GPU 传权重
```

现在的目标是：

```text
每个请求只做几次组件级切换
denoise loop 内零权重传输
```

574GB RAM 已经超过现有双 5090 H3 DLO recipe 所建议的 384GB 级主机容量，因此 host-side BF16 权重、pinned buffers 和 staging 不再是主要限制。

# 三、第一条应该跑的 vLLM-Omni 配置

先使用 **BF16 Turbo merged checkpoint**，完全避开当前 SM120 FP8 噪声问题。

```bash
export MODEL=/home/isaac/Data/h3_weights/MiniMax-H3-Turbo-v4s600ema/FL2VA
export PORT=8091

CUDA_VISIBLE_DEVICES=0,1,2,3 \
VLLM_WORKER_MULTIPROC_METHOD=spawn \
VLLM_OMNI_VIDEO_SYNC_TIMEOUT=1800 \
vllm serve "${MODEL}" \
  --omni \
  --host 0.0.0.0 \
  --port "${PORT}" \
  --trust-remote-code \
  --num-gpus 4 \
  --tensor-parallel-size 4 \
  --text-encoder-tp-size 4 \
  --usp 1 \
  --ring 1 \
  --vae-patch-parallel-size 4 \
  --vae-parallel-mode tile \
  --vae-use-tiling \
  --enable-distributed-layerwise-offload \
  --dlo-no-use-allgather \
  --dlo-resident-layers 40 \
  --diffusion-attention-backend CUDNN_ATTN \
  --enforce-eager \
  --enable-diffusion-pipeline-profiler
```

注意这里**没有**：

```text
--quantization fp8
```

DLO 在这条配置里的作用不是长期流式搬运大量 DiT block，而是：

```text
让 TE/VAE 在阶段间进出 GPU
并给 DiT residency 提供可调节空间
```

## Residency 调节顺序

从：

```text
40 resident blocks
```

开始，依次测试：

```text
40
44
47
50
```

固定：

```text
864×480
124 frames
6 NFE
同 prompt
同 seed
```

停止增加的条件：

```text
峰值显存超过约 30.5GB/GPU
CUDA OOM
显存碎片导致第二次请求失败
```

最终目标是：

```text
dlo_resident_layers = 50
```

也就是 50 个主体 DiT block 全部常驻，denoise loop 中没有 block weight streaming。

即使 50 放不下，47 或 48 也意味着每次 forward 只需处理两三个 nonresident block，和之前 resident=20 时每次传 30 个 block 完全不同。

# 四、请求参数改用 NFE，不再使用模糊的 steps

你已经验证当前两套 engine 的某些版本存在：

```text
num_inference_steps = sigma point 数
实际 DiT forward = num_inference_steps - 1
```

所以客户端应以 NFE 为源数据。

## Balanced production

```yaml
requested_nfe: 6
engine_num_inference_steps: 7
resolution: 864x480
frames: 124
fps: 24
video_flow_shift: 12.0
audio_flow_shift: 3.0
turbo_lora: v4_step600_ema
```

## Fast

```yaml
requested_nfe: 4
engine_num_inference_steps: 5
resolution: 864x480
```

## Quality

```yaml
requested_nfe: 8
engine_num_inference_steps: 9
resolution: 864x480
```

每次启动时从 log 或 profiler 确认 observed forward count，不能永久假定某个上游版本都保持 `N−1` 语义。

# 五、四卡 topology 应该如何选择

第一条必须是：

```text
TP4 × Ulysses1
```

原因是 32GB 卡首先需要切 DiT 权重。

然后再比较：

```text
TP2 × Ulysses2
```

不要一开始使用：

```text
TP1 × Ulysses4
```

因为 Ulysses 只切 sequence，不切 DiT 权重；单张 5090 无法 resident BF16 DiT。

现有 4-GPU H3 benchmark 中，在 B300 上：

| Topology       |     T2V |    I2V |
| -------------- | ------: | -----: |
| TP2 × Ulysses2 | 11.060s | 6.470s |
| TP1 × Ulysses4 |  7.298s | 6.137s |
| TP4 × Ulysses1 |  7.545s | 6.441s |

但 B300 使用的是高带宽互连，不能直接推导 PCIe 5090 的胜者；该 PR 也仍在等待真正的 SM120 和 PCIe 卡验证。

对你的 PCIe-only 5090，先跑：

```text
T1: TP4 + U1
T2: TP2 + U2
```

固定其他全部参数。

我的先验判断：

```text
TP4:
更容易放下
执行模型简单
但每层 row-parallel all-reduce 跨4卡

TP2+U2:
权重每卡更大
增加 Ulysses all-to-all
但部分 GEMM 和 attention 切分更平衡
```

哪一个更快完全取决于你的 PCIe/P2P 拓扑。

# 六、必须先验证四卡 PCIe 拓扑

四张 5090 没有 NVLink。多卡 H3 的速度会严重依赖：

* 每张卡是 x16、x8 还是更低；
* 是否跨 CPU socket；
* GPU peer-to-peer 是否开启；
* ACS/IOMMU 是否阻断 P2P；
* 哪两张卡共享同一个 PCIe switch。

运行：

```bash
nvidia-smi topo -m
nvidia-smi topo -p2p r
nvidia-smi topo -p2p w

lspci -vv | grep -E "NVIDIA|LnkCap|LnkSta"
numactl --hardware
```

CUDA P2P：

```bash
git clone https://github.com/NVIDIA/cuda-samples.git
cd cuda-samples
make -j"$(nproc)" SMS=120
./bin/x86_64/linux/release/p2pBandwidthLatencyTest
```

NCCL：

```bash
git clone https://github.com/NVIDIA/nccl-tests.git
cd nccl-tests
make -j"$(nproc)" CUDA_HOME=/usr/local/cuda

./build/all_reduce_perf -b 8M -e 1G -f 2 -g 4
./build/alltoall_perf  -b 8M -e 1G -f 2 -g 4
```

重点记录：

```text
GPU0↔GPU1
GPU2↔GPU3
跨 pair
all-reduce algorithm bandwidth
all-to-all bandwidth
```

如果拓扑是：

```text
GPU0/GPU1 同一 PCIe switch
GPU2/GPU3 同一 PCIe switch
```

则 TP2×U2 应将：

```text
TP group A = GPU0, GPU1
TP group B = GPU2, GPU3
```

不要把 TP pair 配成：

```text
GPU0, GPU2
GPU1, GPU3
```

# 七、这次升级如何帮助定位 FP8 噪声

更重要的是，四卡让你第一次可以做真正决定性的控制实验。

以前双卡上：

```text
FP8 和 DLO 必须同时开启
```

因此无法分辨：

```text
kernel 错
还是 DLO 错
还是 TP2 错
```

现在可以拆开。

## 实验 F0：BF16 TP4

```text
DiT BF16
TE BF16
TP4
Turbo 6 NFE
```

这是最终 correctness oracle。

## 实验 F1：只量化 TE

```text
DiT BF16
TE FP8
TP4
```

如果输出噪声：

```text
TE FP8 有问题
```

## 实验 F2：只量化 DiT

```text
DiT FP8
TE BF16
TP4
```

如果噪声：

```text
问题位于 DiT FP8 Linear path
```

## 实验 F3：global FP8，DiT 最大 residency

```text
global FP8
TP4
resident 50
```

如果：

```text
resident 50 正常
resident 20 噪声
```

则 DLO reconstruction/prefetch 是主因。

如果：

```text
resident 50 仍噪声
```

则更可能是 SM120 FP8 Linear kernel、量化 scale 或 TP layout。

## 实验 F4：BatchInvariant

```bash
VLLM_BATCH_INVARIANT=1
```

保持 FP8 权重、scale、TP 和 DLO 不变，但绕过原生 FP8 GEMM，用反量化后的 BF16 Linear 做 forward。

如果恢复正常：

```text
权重、scale、TP、DLO 大体正确
SM120 FP8 kernel path 是主因
```

# 八、当前 vLLM PR 状态发生了变化

PR #5910 现在已经不再是 draft，当前 head 是：

```text
1a9b9c2c13c97763567405f43c5fee994c43ab13
```

它现在明确宣称：

* global FP8 同时覆盖 DiT 和 Qwen3-VL TE；
* 可以 fully resident；
* 可以普通 layerwise offload；
* 可以 DLO no-AllGather；
* 在线量化逐层执行，避免完整 BF16 TE 与 FP8 replacement 同时占用显存。

因此你之前使用的旧 head 不应继续作为最终结论。要做 FP8 复测，应单独建立：

```text
pr5910-head-1a9b9c2
```

环境，不能直接覆盖已经可复现的旧环境。

不过该 PR 的公开验证仍主要来自 B300，并没有证明 SM120 TP4 的 FP8 数值正确。因此它适合重新测试，不适合未经验证直接进入 production。

# 九、SGLang 应该承担什么角色

SGLang 当前 FP8 TE PR 仍未合并，而且处于不可直接 merge 状态。它在两张 RTX 5090 上验证了 TE FP8 本身没有明显视觉质量回退，但其主要收益是 host RAM，而不是推理速度。

所以现在 SGLang 最适合承担：

```text
BF16 TP4 correctness control
与 vLLM 做 apples-to-apples 性能比较
```

建议配置思想：

```text
DiT BF16 TP4 resident
TE BF16 fold/TP4
只 offload text_encoder,vae
不 offload dit
Turbo 6 NFE
```

也就是：

```bash
sglang serve \
  --model-path "${TURBO_ROOT}" \
  --model-variant fl2va \
  --num-gpus 4 \
  --tp-size 4 \
  --ulysses-degree 1 \
  --encoder-parallel fold \
  --performance-mode speed \
  --layerwise-offload-components text_encoder,vae \
  --enable-torch-compile false \
  --port 30010
```

核心检查：

```text
启动 log 中 dit 不应进入 layerwise offload
text_encoder 和 vae 可以 offload
denoise 时 PCIe 不应持续搬 DiT block
```

如果 SGLang BF16 TP4 正常，而 vLLM BF16 TP4 异常，那么问题不是 FP8，而是 engine path。

# 十、1TB SSD 的存储规划

1TB 足够，但不能随意保留重复副本。

建议：

```text
/data/h3/
├── base/
│   └── MiniMax-H3/
│       └── FL2VA/
├── merged/
│   └── Turbo-v4-step600/
│       └── FL2VA/
├── loras/
├── hf-cache/
├── modelscope-cache/
├── engine-cache/
└── outputs/
```

只保留一个公共副本的：

```text
text_encoder
video_vae
audio_vae
tokenizer
processor
```

Turbo merged 目录只实体保存：

```text
transformer shards
config/index
```

其他组件用 symlink 或 reflink 指向 base。

第一阶段不要同时保留：

```text
FL2VA base
Ref2VA base
FL2VA Turbo merged
Ref2VA Turbo merged
多个 HF cache 副本
多个 ModelScope cache 副本
```

建议长期预留：

```text
至少 150–200GB SSD 空闲
```

用于：

* safetensors mmap；
* online quantization 临时状态；
* build wheels；
* profiler traces；
* 视频输出；
* crash dump。

574GB RAM 已足够，不要把同一块 1TB SSD 用作高负载 swap：

```bash
sudo sysctl vm.swappiness=1
```

生成期间：

```bash
vmstat 1
```

确保：

```text
si = 0
so = 0
```

# 十二、我对速度的最新预判

这部分是工程估算，不是实测承诺。

对于：

```text
4×5090
BF16 TP4
864×480
Turbo 6 NFE
DiT 基本全 resident
```

合理目标区间是：

```text
warm E2E：约 15–28 秒
```

4 NFE：

```text
约 12–22 秒
```

8 NFE：

```text
约 22–35 秒
```

真正决定最终数字的是：

```text
PCIe topology
NCCL collectives
DiT 是否完全 resident
每个 NFE 的 wall time
VAE decode 是否并行/tiling
```

因此现在 **<30 秒不再依赖 FP8 成功**。这是这次升级最大的意义。

对于 native 768P：

```text
6 NFE + 4×5090
```

可能进入大约 30–55 秒区间，但是否能低于 30 秒仍需要实测。若 768P 硬性要求 30 秒，更现实的生产组合仍可能是：

```text
864×480 H3 Turbo
→ 第二阶段视频超分到 768P
```

# 最终建议

现在立刻停止把双卡 FP8 噪声问题作为 production blocker。新的执行顺序应是：

```text
1. 检查4卡 PCIe/P2P/NCCL
2. 部署 BF16 Turbo TP4
3. TE/VAE stage offload，DiT resident
4. residency 从40升到50
5. 用6 NFE验证 864×480 是否已经 <30s
6. 比较 TP4 与 TP2×U2
7. 再用4卡做 FP8 component isolation
8. FP8 correctness 通过后才考虑生产化
9. SM120 attention、compile、Cache-DiT 最后加入
```

**我最推荐的第一生产候选已经从“global FP8 TP2＋DLO”改为：**

```yaml
gpus: 4x RTX 5090
engine: vLLM-Omni
dit: BF16 Turbo merged
parallelism: TP4
text_encoder: BF16 TP4, stage-offloaded
vae: stage-offloaded, tile4
dit_resident_layers: 47–50
nfe: 6
resolution: 864x480
attention: CUDNN_ATTN
compile: false
cache: false
```

先用这条路线测出无噪声、稳定的真实速度。只要它已经低于 30 秒，当前 SM120 FP8 bug就可以从“必须马上解决”降级为后续性能研究。
